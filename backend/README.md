# Modulus17 Backend

NestJS + TypeScript + MongoDB (Mongoose) API for the Modulus17 React Native To-Do assignment.
Provides email/password authentication (JWT) and per-user task CRUD.

## Stack

- **NestJS 11** (Express platform), TypeScript, CommonJS
- **MongoDB** via **Mongoose** (`@nestjs/mongoose`)
- **Auth**: custom JWT (`@nestjs/jwt` + `passport-jwt`), passwords hashed with `bcryptjs`
- **Validation**: `class-validator` / `class-transformer` (global `ValidationPipe`)
- **Docs**: Swagger / OpenAPI at `/api/docs`
- **Tests**: Jest (unit) + Jest/Supertest e2e against an in-memory MongoDB (`mongodb-memory-server` — no real database needed to run the test suite)

## Project structure

```
src/
  auth/            # register/login/me, JWT strategy + guard, DTOs
  users/            # User schema + service (password hashing lives in AuthService)
  tasks/            # Task schema, DTOs, service, controller (all routes scoped to the caller)
  common/           # cross-cutting: exception filter, ObjectId pipe, @CurrentUser decorator
  config/           # env loading + startup validation
  app.module.ts / main.ts
test/
  *.e2e-spec.ts     # black-box HTTP tests against a real (in-memory) MongoDB
  utils/test-app.ts # shared test bootstrap
```

## Setup

1. **Install dependencies**
   ```bash
   npm install
   ```

2. **Configure environment** — copy the example and fill in real values:
   ```bash
   cp .env.example .env
   ```
   | Variable | Meaning |
   |---|---|
   | `PORT` | HTTP port (default `3000`) |
   | `MONGODB_URI` | MongoDB connection string — local (`mongodb://127.0.0.1:27017/modulus17`) or [Atlas](https://www.mongodb.com/cloud/atlas/register) (`mongodb+srv://...`) |
   | `JWT_SECRET` | Long random string. Generate one: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
   | `JWT_EXPIRES_IN` | Token lifetime, e.g. `7d` |

   The app validates these at startup and refuses to boot with a clear error if any are missing/malformed.

3. **Have a MongoDB instance reachable** at `MONGODB_URI`. Two options — pick one:
   - **MongoDB Atlas** (recommended — no local install, works from a phone/emulator too): see [Connecting to MongoDB Atlas](#connecting-to-mongodb-atlas) below.
   - **Local MongoDB** via Docker: `docker run -d -p 27017:27017 --name modulus17-mongo mongo:7`, then leave `MONGODB_URI` as the default `mongodb://127.0.0.1:27017/modulus17`.
   - You do **not** need either of these to run the test suite — tests use an in-memory MongoDB automatically (see [Testing](#testing)).

4. **Run**
   ```bash
   npm run start:dev     # watch mode
   npm run build && npm run start:prod   # compiled
   ```
   Server: `http://localhost:3000`
   Swagger UI: `http://localhost:3000/api/docs`

## Connecting to MongoDB Atlas

The app doesn't need any code change to use Atlas — `MONGODB_URI` is passed straight through to Mongoose, which accepts both `mongodb://` (local) and `mongodb+srv://` (Atlas) connection strings identically.

1. **Create a cluster.** Sign up / log in at [cloud.mongodb.com](https://cloud.mongodb.com), create a project, then **Build a Database → M0 (Free)**. Any cloud provider/region is fine — pick one close to you. Wait for it to finish provisioning (a couple of minutes).

2. **Create a database user.** In the cluster's **Database Access** tab → **Add New Database User**. Choose *Password* authentication, pick a username (e.g. `modulus17`), and **let Atlas autogenerate the password** (click "Autogenerate Secure Password") rather than typing your own — it avoids needing to know which characters need URL-encoding later. Copy the generated password somewhere safe immediately; Atlas won't show it again. Give the user *Read and write to any database* (built-in role `readWriteAnyDatabase`, or scope it to a `modulus17` database only if you prefer).

3. **Allow your IP.** In **Network Access** → **Add IP Address**:
   - Click **Add Current IP Address** if your IP is stable, or
   - For a laptop that changes networks often during development, use **Allow Access from Anywhere** (`0.0.0.0/0`). This is fine for a throwaway assignment cluster with a strong autogenerated password, but is **not** something to do on a cluster holding real data.

4. **Get the connection string.** On the cluster's **Overview** page, click **Connect → Drivers**, choose **Node.js**, and copy the connection string shown. It looks like:
   ```
   mongodb+srv://modulus17:<db_password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
   ```

5. **Fill in the password and database name**, then paste the result into **`backend/.env`**, replacing the `MONGODB_URI` line:
   - Replace `<db_password>` with the password from step 2. If it contains any of `: / ? # [ ] @ % space`, URL-encode just that password (e.g. via `node -e "console.log(encodeURIComponent('your-password'))"`) before pasting it in.
   - Insert `modulus17` as the database name right after `.net/` and before the `?`:
   ```
   MONGODB_URI=mongodb+srv://modulus17:<encoded-password>@cluster0.xxxxx.mongodb.net/modulus17?retryWrites=true&w=majority&appName=Cluster0
   ```

I never need to see the actual password or connection string — just edit `MONGODB_URI` in your local `backend/.env` directly; it's already git-ignored (see [Security notes](#security-notes)).

## Testing

```bash
npm test          # unit tests (Jest)
npm run test:e2e  # e2e tests — spins up an in-memory MongoDB automatically
npm run lint       # ESLint
npm run build      # TypeScript compile check
```

The e2e suite (`test/*.e2e-spec.ts`) boots the real `AppModule` (real guards, real validation, real Mongoose queries) against a `mongodb-memory-server` instance and covers:
registration, duplicate-email rejection, login (correct/incorrect credentials), `/auth/me` (with/without/invalid token), task CRUD, filtering by status, and — importantly — that **one user can never read, update, or delete another user's task** (verified to return `404`, not just blocked).

## Verifying a real MongoDB connection

Once `MONGODB_URI` in `.env` points at Atlas (or local Mongo), confirm it end-to-end:

```bash
# 1. Start the backend
npm run start:dev
```
Watch the startup log: `Nest application successfully started` with no Mongo connection error following it is a good sign, but isn't proof by itself — Mongoose buffers commands and only surfaces a bad URI/credentials/IP-allowlist problem once a query actually runs. The real confirmation is a successful write in step 2.

```bash
# 2. Confirm the database connection works — register a user.
# A 201 response here is only possible if the app actually reached MongoDB
# and inserted a document, so this *is* the connection proof.
curl -s -X POST http://localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"Password123"}'
```
If this hangs for ~30s and then errors, or returns a 500, it's almost always one of: wrong password in the URI (not URL-encoded), current IP not in Atlas's Network Access list, or the database user doesn't have write access — all fixable in the Atlas dashboard, no code changes needed.

```bash
# 3. Open Swagger (in a browser)
http://localhost:3000/api/docs
```

```bash
# 4. Exercise the rest of the flow — copy the accessToken from step 2's
# response and paste it below (no jq needed/assumed):
export TOKEN="paste-the-accessToken-value-here"

# Login
curl -s -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"alice@example.com","password":"Password123"}'

# Who am I
curl -s http://localhost:3000/auth/me -H "Authorization: Bearer $TOKEN"

# Create a task
curl -s -X POST http://localhost:3000/tasks \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"Finish assignment","deadline":"2025-06-02T18:00:00.000Z","priority":"high"}'
# copy the "_id" from the response for the next two commands

# List tasks
curl -s http://localhost:3000/tasks -H "Authorization: Bearer $TOKEN"

# Mark complete (replace :id)
curl -s -X PATCH http://localhost:3000/tasks/:id \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"isCompleted":true}'

# Delete
curl -s -X DELETE http://localhost:3000/tasks/:id -H "Authorization: Bearer $TOKEN"
```

Then check the Atlas dashboard (**Browse Collections** on the cluster) — you should see a `modulus17` database with `users` and `tasks` collections containing real documents. That's the definitive end-to-end confirmation.

## API summary

All request/response bodies are JSON. Protected routes require `Authorization: Bearer <accessToken>`.

### Auth

| Method | Path | Auth | Body | Notes |
|---|---|---|---|---|
| POST | `/auth/register` | — | `{ email, password }` | password: min 8 chars, at least 1 letter + 1 digit |
| POST | `/auth/login` | — | `{ email, password }` | generic 401 on any invalid credential |
| GET | `/auth/me` | ✅ | — | returns the current user, never the password hash |

### Tasks (all require a Bearer token; always scoped to the caller)

| Method | Path | Body / Query | Notes |
|---|---|---|---|
| GET | `/tasks` | `?status=all\|pending\|completed&priority=low\|medium\|high&sort=createdAt\|deadline\|priority` | all params optional |
| POST | `/tasks` | `{ title, description?, scheduledAt?, deadline?, priority?, category? }` | `title` required; `priority` defaults to `medium` |
| GET | `/tasks/:id` | — | 404 if missing **or** owned by another user |
| PATCH | `/tasks/:id` | any subset of the above + `{ isCompleted? }` | partial update |
| DELETE | `/tasks/:id` | — | 404 if missing **or** owned by another user |

Full request/response schemas: `/api/docs` (Swagger) once the server is running.

A full copy-pasteable curl walkthrough (register → login → me → create/list/update/delete a task) is in [Verifying a real MongoDB connection](#verifying-a-real-mongodb-connection) above.

## Error shape

Every error response (validation, auth, not-found, duplicate email, unexpected) is normalized by a global exception filter to:

```json
{
  "statusCode": 400,
  "message": "…",
  "error": "Bad Request",
  "path": "/tasks",
  "timestamp": "2025-01-01T00:00:00.000Z"
}
```

## Security notes

- Passwords are hashed with bcrypt (12 salt rounds) — never stored or logged in plaintext.
- `passwordHash` is excluded from the schema by default (`select: false`) **and** every response is built from an explicit safe-user mapping — it can never leak, even by accident.
- Login returns the same generic "Invalid email or password" message whether the email doesn't exist or the password is wrong, to avoid account enumeration.
- Every task query/update/delete is filtered by the authenticated user's id at the database level — accessing another user's task by id returns `404`, not `403`, so existence can't be inferred either.
- `.env` is git-ignored; `.env.example` documents required variables without real values.
